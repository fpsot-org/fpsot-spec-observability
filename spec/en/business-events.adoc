= Business events for process mining
include::_fpsot-terms.adoc[]

These rules set the events that record the steps of business processes.
Process mining reads such events to find how a process runs in fact, where work waits and where it loops.
No standard sets these events yet, so {abbr-fpsot-first} defines them here.

A business event records one step of a process, such as the review of an application.
It names the activity, the change in its lifecycle and every business object that the step touches.
An export tool can then turn the events into an object-centric event log, under OBS-086.

== The event

[[OBS-070]]
*OBS-070.* A component MUST emit an explicit business event at each boundary of each business step that its inventory lists.
The event MUST have the `EventName` `org.fpsot.observability.activity.transitioned`.
It MUST carry the attribute `org.fpsot.stream` with the value `business`.
A tool MUST NOT infer business events from {abbr-http-first} spans or from database changes.
All business events share one structure, so one event name fits them, as the semantic conventions ask.
The link:https://www.vdaalst.com/publications/p658.pdf[Process Mining Manifesto] notes that technical events need grouping into business activities before they mean anything.

[[OBS-071]]
*OBS-071.* Each business event MUST carry the attribute `org.fpsot.activity.key`, with the code of one concept of an activity scheme.
The code MUST follow VOC-005, VOC-006 and VOC-064, such as `review-application`, and MUST NOT be a label.
The scheme MUST follow the vocabularies specification, and the inventory names it with its version.
One code MUST stand for one business step, and the lifecycle of OBS-072 gives its state.
The labels come from the scheme in both languages, so a bilingual system never splits one activity in two.

[[OBS-072]]
*OBS-072.* Each business event MUST carry the attribute `org.fpsot.lifecycle`, with a code from this table.

[cols="1,2,2",options="header"]
|===
|Code |Meaning |Label in French
|`schedule` |Someone planned the step, or put it in a queue. |planification
|`start` |Work on the step began. |début
|`suspend` |Work on the step paused. |suspension
|`resume` |Work on the step went on after a pause. |reprise
|`complete` |The step ended with its result. |achèvement
|`abort` |The step ended without its result. |abandon
|===

A step that takes no time MUST emit only `complete`.
A step that takes time MUST emit at least `start`, and then `complete` or `abort`.
These events MUST carry the same activity key and the same objects.
An event log needs both ends of a step.
It can then tell the time that a step waits from the time that it takes.

This note is informative.
The codes and labels of this table will move to a concept scheme of the vocabularies specification.
The activity keys of OBS-071 live in such a scheme already, and the codes will stay the same.

This note is informative.
A tool that writes the lifecycle extension of link:https://standards.ieee.org/ieee/1849/10907/[XES] can map the codes as follows.

[cols="1,2",options="header"]
|===
|Code |Transition in XES
|`schedule` |`schedule`
|`start` |`start`
|`suspend` |`suspend`
|`resume` |`resume`
|`complete` |`complete`
|`abort` |`ate_abort` after a `start`, and `withdraw` before any `start`
|===

{abbr-ocel-first} 2.0 has no lifecycle of its own, so OBS-086 exports the code as an event attribute.

== Objects

[[OBS-073]]
*OBS-073.* Each business event MUST carry the attribute `org.fpsot.objects`, a list of one or more object references.
Each reference MUST be a map with exactly three members.

* `type` is the name of a class of the data models specification, or of the LinkML schema of the product.
The inventory names each such class, which follows DMO-020, such as `PartyRole` or a product class `Application`.
* `id` is the internal identifier of the object, as a string under DAT-060 and DAT-061.
A {abbr-uuid-first} takes the canonical form of DAT-065.
* `qualifier` is a kebab-case code for the role of the object in this event, such as `subject` or `co-applicant`.

A log store that cannot hold lists of maps MAY use flat attributes instead, of the form `org.fpsot.object.<type>.<qualifier>.ids`.
The type and the qualifier are then in snake_case, as OBS-022 asks, and the value is a list of identifiers.
An example is `org.fpsot.object.party_role.co_applicant.ids`.
A tool that converts between the two forms MUST lose no reference.
One step can touch several objects, such as an application, a payment and a permit.
A single case number would hide that.

The conversion is reversible, because a class name treats each abbreviation as one word, under NAM-011.

* To get the snake_case type, put `_` before each capital letter but the first, then use lower case.
`PartyRole` becomes `party_role`.
* To get the class name back, write the first letter of each word in capitals, then drop each `_`.
* The qualifier changes each `-` into `_`, and back.

[[OBS-074]]
*OBS-074.* A component or a tool MUST NOT use a trace identifier to identify a case or a business object.
The same holds for a span identifier.
Trace and span identifiers show where a record came from, and nothing more.
A business case lasts for days and spans many requests, while one request can touch several cases.

[[OBS-075]]
*OBS-075.* A business event SHOULD carry `org.fpsot.performer.role`, with the code of the role or unit that did the step.
An example is `case-officer`, from a scheme of the operator under VOC-064.
The event MAY also carry a `performer` object reference to the person, when the {term-privacy-impact-assessment} allows it.
That reference names a real person by an identifier under OBS-092, and an export replaces it under OBS-087.
It MUST NOT point to a role or a unit, which the role attribute holds.
A role is enough to study a process, while a person identifier turns process mining into the monitoring of staff.

== Models and corrections

[[OBS-076]]
*OBS-076.* When a {abbr-bpmn-first} model describes the process, each business event SHOULD carry three attributes.
They are `org.fpsot.bpmn.process.id`, `org.fpsot.bpmn.process.version` and `org.fpsot.bpmn.element.id`.
The element identifier is the `id` of the task or event in the model.
Each version of a model MUST stay unchanged and reachable once a component has used it.
Conformance checking compares each event with its model element, in the version that applied at the time.

[[OBS-077]]
*OBS-077.* An activity key, a qualifier or an event name MUST NOT hold free text or personal information.
It MUST NOT hold a value that belongs to one case either.
Such values belong in the objects of OBS-073 or in other attributes.
A key that varies per case breaks the counts of process mining, and can leak personal information into every report.

[[OBS-078]]
*OBS-078.* A component or a log store MUST NOT change or delete a business event before its retention ends.
To fix a wrong event, a component MUST emit a new event with the attribute `org.fpsot.event.corrected_event.id`.
That attribute holds the `org.fpsot.event.id` of the wrong event.
A log that a system rewrites after the fact gives results that nobody can repeat.

[[OBS-079]]
*OBS-079.* The inventory SHOULD name, for each process, the object type that serves as its main case, such as `Application`.
A tool that needs one case per event can then build it in the same way each time.
