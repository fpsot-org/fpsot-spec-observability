= FPSOT observability specification
include::_fpsot-terms.adoc[]

This specification sets how software of the {abbr-fpsot-first} records logs, traces and metrics.
It also sets how a public body keeps, protects and destroys those records.
The same records serve three kinds of readers.
Some run the software, some audit it and some study its processes.

The rules build on link:https://github.com/open-telemetry/opentelemetry-specification/blob/18c5c1706e346fec3bdb5e135a6e3a78f461e586/specification/logs/data-model.md[OpenTelemetry], an open standard of the Cloud Native Computing Foundation.
They name capabilities and standards, not products.
Products appear only on the informative page on implementation profiles.

== Parties and streams

The rules address three parties.

* A component is a program that emits records, such as a service or a batch job.
* A log store is the system that receives records, keeps them and destroys them on schedule.
It includes any collector between the components and the storage.
* The operator is the public body that runs the components and the log store, and that answers for its records.

Each event belongs to one of three streams, under OBS-014.

* The technical stream helps the people who run the software, with errors, warnings and diagnostic records.
* The audit stream records who did what to which information, for security and for accountability.
* The business stream records the steps of business processes, for process mining.

== Parts

The rules come in ten parts, and two informative pages follow them.

* xref:inventory.adoc[Log inventory and schema] sets the file that lists what each component records.
* xref:records.adoc[Records, names and time] sets the record model, the names, the identifiers and the timestamps.
* xref:audit-events.adoc[Audit events] sets which events the audit stream records.
* xref:traces.adoc[Traces and propagation] sets how a request carries its trace from one service to the next.
* xref:metrics.adoc[Metrics] sets the measurements, including the health of the log pipeline.
* xref:business-events.adoc[Business events for process mining] sets the activity, the lifecycle and the objects of each business step.
* xref:export.adoc[Export and transport] sets the output formats and how records reach the log store.
* xref:privacy.adoc[Privacy and minimization] sets what personal information a record may hold.
* xref:retention.adoc[Retention, legal hold and destruction] sets how long records stay and how they go.
* xref:integrity.adoc[Integrity and tamper evidence] sets how a log store proves that nobody changed its records.
* xref:implementation.adoc[Implementation profiles] is informative, and shows how some frameworks meet the rules.
* xref:counsel.adoc[Questions for counsel] is informative, and lists the legal points that a lawyer must settle.

== Related specifications

This specification builds on other {abbr-fpsot} specifications, and cites their rules by number.

* The naming specification sets the form of event names, under NAM-050 and NAM-051.
* The data types specification sets the form of instants and identifiers, under DAT-010 and DAT-063.
* The vocabularies specification sets the concept schemes that hold the activity keys and the purpose codes.
* The security specification sets how a project handles secrets and reports a {term-vulnerability}, under SEC-020 and SEC-040.
* The {abbr-api-first} design specification sets the {abbr-http-first} interfaces and the events between services.
* The testing specification sets the conformance suites, under TST-044 to TST-048.

The FPSOT identity and access specification lists the identity and access events, and sets what each one holds.
This specification sets how a component records any audit event, and how a log store keeps and protects it.

== Profiles

A component or a log store claims one or more profiles.
Each profile is a set of rules that a buyer can require by name.

[cols="2,3,3",options="header"]
|===
|Profile |Who claims it |Rules
|`base` |Each component and each log store |OBS-001 to OBS-004, OBS-010 to OBS-014, OBS-020 to OBS-033, OBS-040 to OBS-046, OBS-080 to OBS-085, OBS-090 to OBS-096, OBS-100 to OBS-106
|`traces-metrics` |Each component that serves or sends requests |OBS-050 to OBS-054, OBS-060 to OBS-063
|`process-mining` |Each component that emits business events, and each tool that exports them |OBS-070 to OBS-079, OBS-086, OBS-087
|`audit-integrity` |Each log store that keeps an audit stream or a business stream |OBS-110 to OBS-117
|===

[[OBS-001]]
*OBS-001.* A component or a log store MUST state, in its inventory under OBS-010, the profiles that it claims.
It MUST meet every MUST rule of each profile that it claims.
Each component and each log store MUST claim the `base` profile.
A component that emits business events MUST claim the `process-mining` profile.
A log store that keeps an audit stream or a business stream MUST claim the `audit-integrity` profile.
A named profile lets a buyer ask for a known set of rules, and tells a tester what to check.

[[OBS-002]]
*OBS-002.* An implementation MUST follow the versions of the outside standards that this page lists under Standards.
It MAY follow a later minor version of the same standard.
This holds only when the parts that it uses keep the same status and meaning.
OpenTelemetry releases often, so a pinned version tells every reader which text applies.

[[OBS-003]]
*OBS-003.* To meet a rule of this specification, an implementation MUST NOT rely on OpenTelemetry features in Development or Alpha.
It MAY use such a feature for another purpose.
It MUST then list the feature and its pinned version in its inventory.
Examples are profiles, entities, the file exporter and the attributes of semantic conventions in Development.
These features can change in any release, and a rule that relied on them would break.

[[OBS-004]]
*OBS-004.* A conformance suite of this specification MUST check the output of an implementation, under TST-044.
The output includes its records, its exports and its checkpoints.
It MUST NOT need the source code of the implementation.
Each rule of this specification names the output that shows it.
A conformance tool will follow in a later version, and the folder `examples/` holds the first fixtures.

== Examples

The folder `examples/` holds three files that meet these rules.

* `log-record.jsonl` is an audit event in the {abbr-json-first} Lines form of OBS-080.
* `business-events.otlp.json` holds three business events in the {abbr-otlp-first} form of OBS-081.
* `ocel-export.json` is the {abbr-ocel-first} 2.0 export of those three events, under OBS-086 and OBS-087.

The script `examples/check-examples.py` checks them, and `examples/test-examples.sh` checks that the script rejects broken copies.

The keywords follow requirement WRT-010 of the {abbr-fpsot} writing specification.
The French version uses the French keywords of WRT-011.

== Legal status

The specification states the practice of {abbr-fpsot}, and it is not legal advice.
Points that need a lawyer sit in informative notes and in the questions for counsel, never in a rule.
